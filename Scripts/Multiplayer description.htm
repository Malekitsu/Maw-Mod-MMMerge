Gameplay overview.

1. Connection establishing

Multiplayer UI in top right corner of ingame menu is dedicated to connection establishing / multiplayer setup.

Multiplayer suggests two types of connections: "LAN" and "Internet". LAN is stands for local network, you should select it if all players belonging to same physical or virtual network, otherwise - select "Internet".

Typically, one player sets 'Host' role and sends his session code to remote players, while other players set their role to 'client', paste host's session code into according field, and send their session code to host. Host fills clients table with received session codes and toggle connection listening, clients click "Connect" button. Once connection establisehed, client goes directly into host's game (game menu forcefully closed), host gets client's line marked with 'LAN', 'p2p' or 'Relay' according to type of established connection. Once all clients marked as joined, host can close multiplayer UI.

Watch the demo to see video example.

If in any case client cannot join host, red "x" mark will be set against host's session code.

There are wide range of reasons why connection cannot be established, if that happens, try to create virtual network using Hamachi or OpenVPN and use LAN connection type.

2. Monsters

In the MM engine, monsters are only active within a certain radius around the player. Increasing this radius leads to a significant increase in performance requirements, and, more importantly, unexpected behavior of monsters outside the original radius, so in multiplayer mode, the control radius is not increased - monsters are controlled by different players. Each player on the map periodically updates the list of active monsters, generates an AI state for them and sends them to other players. If a monster is on the active list of several players at once, the player with the lower ID takes precedence. If a monster attacks or interacts with a player, the target player takes precedence over others, regardless of ID.

3. Limited access to chests and NPCs

To avoid desynchronizations, only one player can interact with the chest at the same time, the chest will be inaccessible for the rest. Only one player can control the dialogue with the NPC, the other participants in the dialogue will be able to see the text, but not activate the dialogue topics.

4. Remote players representation

To represent remote players, puppets are used - monsters whose AI state cannot be changed by the game engine. The data received from the remote player determines the behavior (animations and sounds) of the puppet. Puppet type can be selected in multiplayer settings menu.

Each player notifies all remote players on the same map about every change in his direction and speed. The sent data is not checked by the receiving party and used "as is". To avoid overloading the network, player movement data is not sent in real time, instead it is accumulated and sent as one chunk every 250 milliseconds. This literally reduces the number of packets sent by dozens of times, without sacrificing the accuracy of puppet movement for remote players. A delay of 250 milliseconds does not seem critical for MM gameplay.

5. Spells

The mechanics of casting spells has significant changes in multiplayer mode:

  1. When choosing a spell from the book, the game does not pause, the player can be attacked;
  2. When choosing the target of a spell, the game does not pause, the player and monsters can move, the player can be attacked;
  3. All group-wide spells in single player will also affect remote players within a certain radius (players entering this radius can be seen at the bottom of the spell book screen);
  4. Spells "Fly" and "Water walk" work as auras around the character who cast the spell: they are periodically applied to all remote players within a certain radius for 10 game minutes (20 real seconds).
  5. To quickly cast spells on remote players, you can use additional interface or press ctrl + the player's number in the list of remote players. Also with the help of the interface, you can apply healing and most condition-removal potions to other players.

6. Game pause, rest screen

In most cases where a pause is set in a single player game, the passage of time in multiplayer mode will continue: on the screens of the chest, inventory, spellbook, spell selection, switching to another map. The exception is the home screen: the player inside is protected from monster attacks, but time will continue to run if there is at least one remote player on the map.
To open rest screen to skip time or rest&heal, all players on the same map must be nearby (within a certain radius), food will be shared among remote players, when necessary.

7. Turn-based mode

The rules for monsters synchronization in turn-based mode correspond to the rules for real-time mode.
Each player goes through the combat and movement phases independently of remote players. After the movement phase ends, the player waits for the remote players to be ready, after which the monster movement phase starts, followed by the combat phase again.

8. Time synchronization for players on different maps

Time for players on different maps flows independently. When moving to a map, the transferring player takes the time of the players on the map. This system can lead to unexpected time jumps in both directions, but I have not found a better solution at the moment.

Multiplayer engine overview.

Since the game was not designed with multiplayer in mind, and the game's source code is not available, the synchronization is done as is, and not in the best way possible. Although there is a "host" in the game, the number of server checks is minimal, they are used only where it is necessary to avoid desynchronization (interaction with chests, with NPCs, picking up items). None of the multiplayer algorithms involve passing and running arbitrary code on a remote computer, so system security is respected, but since the network code is open and the number of server checks is minimal, any troll can ruin the game. Therefore, I do not plan to create a lobby, those wishing to play together will have to contact themselves and exchange session codes to connect.
For the same reason, I refused to protect sessions with a password: the host is manually able to turn on and off waiting for new connections, and only those players whose code is pre-specified in the host list can connect.

1. Data transfer

Interaction between players is carried out by exchanging binary data packets (datagrams) via the UDP protocol. Packets can have different sizes and contents, but always have a 24-byte structured header:

field name size (bytes) description
sender_id 2 Id of player, who sent this packet (comes from his Multiplayer.my_id).
packet_code 2 Code of the packet settings from Multiplayer.packet_by_code array.
packet_id 4 Id of the packet, used internally.
part_id 2 Id of the packet part, in case if origin packet was spliited into few due to size, used internally.
parts_total 2 Total amount of parts, used internally.
response_to 4 Id of the packet, this one is responds to, used internally
map_id 2 MapStatsIndex of the map, where was sender, when packet have been sent.
reload_count 2 How many times host reloaded the game, used to sort off packets that were sent before game reload, but arrived after.
bulb_size 4 Size of payload (data, that goes after header)

2. Arbitrary data exchange

For map- and quest-specific data exchange multiplayer provides unified functions and events:

Multiplayer.broadcast_mapdata(t)
t - is any lua value (i.e. boolean, number, string, table), mmext tables won't be sent properly and must be converted to standard lua tables beforehand, tables with cyclic references or repeating cross-references are not allowed (probably will lead to fatal error).
Sends data to all users on same map.

events.MultiplayerUserdataArrived(t)
Will trigger when data, brodacasted by method above, arrives.

Multiplayer.broadcast_mapdata(t, event_name)
t - same as above
event_name - event on remote side to be called, when data arrives (should be registered using 'Multiplayer.allow_remote_event' first)
Sends data to all user on same map.

events.[event_name](t)
Will trigger, when data arrives, t is sent data.

Multiplayer.broadcast_questdata(t, event_name)
same as Multiplayer.broadcast_mapdata, but sends data to all players in the game, event_name is required parameter in this method.

events.[event_name](t)
Will trigger, when related data arrives

Multiplayer.allow_remote_event(event_name)
Allows calling and execution of event, when remote player triggers it using 'Multiplayer.broadcast_questdata' or 'Multiplayer.broadcast_mapdata' method.

Functionality described above is generic wrapping around wider packet handling methods. Check following example, to see how packets are processed underneath.

4. Incoming and outgoing packets archives.

All sent and received packets are preserved for 30 seconds for needs of approval and resend algorithms. Accessing these archives might be useful for debug/experiment purposes: Multiplayer.outgoing_packets() and Multiplayer.incoming_packets() will return them accordingly. Each archive is a lua table, where key is packet id, and value is IncomingPacket object or OutgoingPacket object accordingly. I'll describe some useful fields of these objects below, entire content may be checked by inspecting BasePacket.lua, IncomingPacket.lua and OutgoingPacket.lua scripts from Multiplayer/Network folder.

Common fields:

settings - reference to table from Multiplayer.packet_by_code;
metadata - header data of last received part of this packet;
parts - array of packet parts payload, can be used to check what parts of the packet has not arrived.
timestamp - number - time in seconds, when this packet have been registered, used for resend/approval requests.

IncomingPacket:

processed - boolean - false if some parts of the packet have not arrived yet;
request_timestamp - when resend was requested last time, initially this field is equal to timestamp;
requests_count - how many resend requests were made (there is a limit in Network/Receiver.lua)

OutgoingPacket:

delivery_to - client id, whom this packet have been sent;
delivery_approval_required - copy of packet check_delivery flag;
delivery_approved - boolean - true, if approval required, and delivery was approved;
request_timestamp - when last approval request have been sent, initially equal to timestamp;
requests_count - how many approval requests were made (limit is in Network/Sender.lua)

5. Saved game data

Multiplayer engine stores necessary map, game and remote players data in Saves/MultiplayerGames.bin.
Whenever host saves game, clients update their party data on host side, this allows to rejoin host with any save or game instance and continue playthrough with previoulsy used party.

There are useful pairs of events, if you want to expand saved data:
events.GatherGameData(t) - whenever host saves the game or accepting new client.
events.ProcessGameData(t) - whenever client process server's data on join or game reload.
events.GatherPartySaveData(t) - on save game, on multiplayer data autosave, when host requests client's party data.
events.ProcessPartySaveData(t) - when client receives data from server, or when loads multiplayer party autosave.

t in each event is lua table, that should be populated in "Gather" events and processed in "Process" events.
Note, there is no name checks during gathering, thus overwrites avoidance is user's responsibility.

Unless client joins game very first time, character selection screen will be opened with suggestion to choose "host save", "client save" or current character. Either client save or host save will be marked as "most relevant", depending on time difference of each save and current host's ingame time. While "host save" obvioulsy saved on host side, "client save" comes from two sources: actual save file (autosave or manual save) or multiplayer autosave (Saves/MultiplayerAutosave.bin). Multiplayer autosave performed every 30 seconds and contains only player's party data, it is dedicated to be progress saver in cases of game crash or other unexpected game closure. MultiplayerAutosave.bin is lightweight and contains party data of only one last played game (currently played).
In case if both multiplayer autosave and regular client's save present, only one of these will be displayed on character selection screen, depending on what's save ingame time is differs less than one host have.

6. Saved map data

Along with game data, multiplayer also stores necessary map data. This allows players to simultaneously play on different game maps, with progress being synchronized. Map save data is saved in game save file on host side. Same, as other multiplayer save routines, it has paired events:
events.MultiplayerPrepMapData(t) - whenever remote player enters current map, or player leaves the map.
events.MultiplayerProcessMapData(t, actual) - on events.AfterLoadMap, if any remote map data was received; actual is true, if data received from player, who currently at map.

Also multiplayer provides additional map loading events:
events.BeforeMapHandlersStarted() - on events.AfterLoadMap, but before Multiplayer.leave_map_halt set to false. At this point players positions / monster actions / objects are not synchronized yet.
events.MapLoadingDone() - when all multiplayer map loading routines are done.

7. Multiplayer events extension

Multiplayer widely uses events system of MMExtension and adds a bit of extra functionality, worth to mention:

Multiplayer.events - same as 'events', but handlers are used only if multiplayer mode is on, example:
function events.ExitNPC(i) -- works always
function Multiplayer.events.ExitNPC(i) -- works only if multiplayer is on
All multiplayer scripts use Multiplayer.events instead of events, thus solo game without multiplayer is not affected by the mod at all.

Multiplayer.events.Once(event_name, f)
allows to set handler, that will be executed only once and then removed.

Multiplayer.utils.TickCounter(f, period)
f - function, period - number of ticks to to skip before repeating

Multiplayer.utils.MillisecCounter(f, period)
f - function, period - number of milliseconds to skip before repeating, cannot fire faster, than game "ticking"

Multiplayer.utils.CoTickCounter(co, period)
Multiplayer.utils.CoMillisecCounter(co, period)
Same as functions above, but first parameter is coroutine, and it gets resumed every time period comes in. Once coroutine is 'dead', event handler removed.

Multiplayer packets example

-- Use 'events.MultiplayerInitialized' event to create new packets.
-- Creating new packets in global or map scripts is forbidden due to unpredictable order of scripts execution,
-- what will lead to packet numeration desync and completely undefined behaivor.
function events.MultiplayerInitialized()
    local packets = {
        -- packet name
        send_status_text = {
            -- function for data generation, must return string.
            bulb = function(text)
            local t = {
                expr = math.random(1, 109),
                msg = text
             }
               
             -- to encode comlex types as string, use 'Multiplayer.utils.item_to_bin' function
             return Multiplayer.utils.item_to_bin(t)
          end,
          handler = function(bin_string, metadata)
             -- decode data
             local data = Multiplayer.utils.binstr_to_item(bin_string)
               
             -- handle it
             for i,v in Party do
                v:ShowFaceAnimation(data.expr)
             end
             Game.ShowStatusText(data.msg)
          end,
           
          -- Default value for fields below is false
          same_map_only = false, -- Packet will be ignored, if arrived from player from other map.
          check_delivery = true, -- UDP does not gurantee delivery of datagrams, if this field is set, packet with delivery approval will be sent as response. If sender won't receive delivery apporval in time, packet will be resent.
          compress = true, -- Data of packet will be compressed before sending, and decompressed before passing to handler function. Can significantly reduce packet size, though utilizes more CPU time.
          allow_anonymous = false -- Don't ignore packet if it arrived from unregistered client. Not recommended to set this flag, unless packet used by connection establishing routines.
          gnore_reload_count = false -- If set to true, packet will be processed even if was sent from previous game (before save game load)
       },
       
       request_gold_amount = {
          -- bulb is unncessary
          handler = function()
             return Party.Gold -- value returned by handler function will be directly passed to bulb function of response packet.
          end,
          response = 'tell_gold_amount', -- When this packet arrives, response packet will be automatically sent back.
          check_delivery = true
       },
       
       tell_gold_amount = {
           bulb = function(value)
             return Multiplayer.utils.item_to_bin(value)
          end,
          handler = function(bin_string, metadata)
             local amount = Multiplayer.utils.binstr_to_item(bin_string)
             local name = Multiplayer.client_info(metadata.sender_id).name
             Game.ShowStatusText(string.format("Player %s has %s gold.", name, amount))
          end
       }
    }
    -- Necessary step to assign code to each packet, and initialize service fields.
    Multiplayer.utils.init_packets(packets)
   
    MyMultiplayerFuncs = {}
   
    -- function below can be used from debug console,
    -- turn on multiplayer, and call them with ClientId = 0 to see effect.
    MyMultiplayerFuncs.SendStatusText = function(ClientId, Text)
       Multiplayer.add_to_send_queue(ClientId, packets.send_status_text:prep(Text))
    end
    MyMultiplayerFuncs.RequestGoldAmount = function(ClientId)
       Multiplayer.add_to_send_queue(ClientId, packets.request_gold_amount:prep())
    end
end

Known bugs with no planned fix date (non-critical, no obvious fix)

- When moving to a map where there are remote players, the player's characters may be weakened even if the party has enough food.

- In turn-based mode, if a player has completed the combat and movement phases and is waiting for other players, monster animations may not play.

- In turn-based mode, remote players' movements may have a rubber band effect.

- The position of items dropped by the player may differ slightly for remote players, if the difference is significant, the item will be forcibly relocated.

- Rarely, hostile monsters may start ignoring the player until they take damage from him.
